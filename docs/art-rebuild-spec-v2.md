## 0. 这一版要解决的问题

用户原话归纳为五件事：

1. **所有有代码的美术素材**（动态 / 静态 / 物品 / 人类）都要重构建模优化，尤其可交互物「实在太丑」。
2. **池塘不对**：加锦鲤；金蟾参考网络图片重做，不要简单几何体堆砌；金币不要「金色原型几何体」。
3. **交互物要真实**：扔完金币要沉底可见，**数据不清理**，像现实水池里日积月累的硬币。
4. **人与人交互不好**：合十很丑，和尚尤其要重建；新增实时在线聊天——选一个和尚打招呼 / 聊天，打招呼是合十行礼（评估是否加短动画），聊天是气泡式、**仅两人可见**，「像光遇那种感觉」，参照《燕云十六声》。
5. **撸猫**：猫的建模「非常非常丑」，需与放大面板一起重做。

**本轮交付顺序**：先出本文档 → 再以提问方式补全风险与更优建议 → **得到确认后才进入开发**。

五个 GLB 全部 `extensionsUsed=[]`、`images=0`，材质靠语义名被 `applyGameMaterials()` / `applyCourtMaterials()` 覆盖成纯色。**即：约 11.5 万三角面全花在光滑纯色球体上，是典型「高面数、低信息量」，而且所有动作都是代码逐帧硬改变换硬凑出来的。**

**四个更深的技术根因（比「几何体堆砌」更致命）**：

1. **零 PBR 通道**：无 baseColor / normal / roughness / AO 贴图，无骨骼、无 morph、无动画，材质全靠纯色 → 怎么打光都塑料。
2. **运行时用绝对值逐帧覆盖模型变换，把 Blender 里建好的形压变形**：`updatePond()` 1900 每帧 `toadParts.body.scale.set(1.2, 0.82+sin, 1.02)`，而 GLB 里 `toadBody` 实测 `scale=(1,1,1)` → 精心放样的拱背被强行 X 拉伸 20% / Y 压扁 18%；`grpCoin` GLB 实测 `T=(0,0.615,0.515)`，代码却写 `coin.position.y=0.7`，每帧抬高 8.5 cm；`eyes[].scale.y=1.15` 把眼球常态拉长。**重建后必须改成「记录 GLB 基准值 + 增量」，否则新模型照样被压丑。**
3. **池塘 y 层次错乱（加锦鲤 / 金币沉底的硬前置）**：`ground` 是 y=0 的 200×200 **不透明**平面；水面 y=0.035、池底 y=0.012，但沉底金币 y=0.045、荷叶 y=0.05、涟漪 y=0.06 —— **金币其实漂在水面之上，池底根本没东西**；`pondFish` 基位 y=−0.6 在地面之下，所以只能做「跃出」而不能常驻游动。详见 §5.3。
4. **draw call 失控**：单人场景约 **660 draw call**，满员 50 同修再 +49×68 ≈ **4000 draw call / 1.1M tris**，且 `addPeer()` 2667 对每个 mesh 都开 `castShadow`，阴影 pass 再翻倍。这是手机端最大的隐患，比面数更严重。

**根因判断（最关键的一条）**：
> 现在画面里同时存在 **三套造型语言**——准写实国风建筑（court.glb）／Q 版几何角色（和尚、猫、金蟾）／扁平低模植物（松、银杏）。「丑」主要不是某个模型面数不够，而是**三者摆在一起互相拆台**，加上放大面板还在用 CSS 拟物画法，形成第四套语言。只提高单个模型精度不会解决问题，必须先定统一宪章 + 修掉上面四个技术根因。

### 3.2 三条路线

> **两位专家独立评估后一致表态**：走 A，并把名字定准为 **「国风写意写实 / 泥塑木雕质感的 stylized realism」**——不是纯 low-poly，也不是照片级写实。理由：纯 low-poly 撑不起「真实、像成品」，照片写实会推翻水墨留白与 3+1 色板；泥塑/木雕/石雕本身自带手工体块与温润哑光，正好是中间态。
> **重建范围共识**（两位专家已消歧）：**「13」与「15」不是冲突，是两种计数单位** —— 13 = 美术规格条目数（按姿态 / 视角 / 状态拆，含重复），15 = 工程资产种类（`game.js:1696` 实测 9 类交互热点 33 实例 + 6 类动态非热点），明细见 §2。对外一律用 **15 类资产**。松/银杏与 9 张面板 sprite 随本轮一并换皮；**`court.glb` 静态建筑不推翻**，只补 PBR 贴图。
> **比例锚点定案**：彻底废弃「几头身」表述，改用 §4.1.1 的四条可机读量；**侧视定稿图为唯一比例锚点**，正视图只作五官 / 交领右衽 / 广袖 / 笔触 / 留白参考，规则直接援引 `art-prompt-pack-v1.md` 第 19/74/93/109 行，**不另立新规范**；侧视稿需裁去平台水印。
> **验收用的 P0 清单**（专家给的「改完应该长什么样」）：① 和尚有肩肘腕与布料垂坠，合十是整条手臂抬起，第三方能看到；② 猫一眼看出是猫且毛流/耳廓/尾根有体积；③ 金蟾能辨铜铸造像工艺；④ 锦鲤有花纹且在水下摆尾巡游；⑤ 池底币累积可见、刷新与换设备都在。

### 3.3 v3 可执行规则（约束角色 / 动物 / 器物 / 水体 / UI）

1. **形体母题**：麦积山石窟「微笑的小沙弥」（细眯眼、微垂首、双手合十置于胸前、衣袂自然垂落）、明清铜三足金蟾造像、唐宋木构与民间泥塑。不照抄照片，取体块与神态。
2. **禁止**：`SphereGeometry / ConeGeometry / CylinderGeometry` 直接作为主体的可见最终表面。允许作为细分、放样、布尔、雕刻的**基底**，但输出必须是连续曲面 + 分件结构。
3. **结构最低集**：和尚必须有颈、肩、上臂/前臂（袖）、腕、手（五指可简化为连指块但要有拇指与掌形）、踝、僧鞋；猫必须有肩胛/髋部过渡、耳廓厚度、口鼻体积、尾根；金蟾必须有鼓膜、腮腺、下颌褶、蹼趾。
4. **材质**（数值已由两位专家共同收敛，见 v1.1 勘误）：布/木/石 `roughness 0.78–0.95 / metalness 0`；**旧铜 `metalness ≤ 0.35`、`roughness 0.5–0.68`**（比初稿的 0.55 更低，避免亮金高光破坏低饱和色板）；统一补 `normal` 微凹凸 + AO。金色只用旧金 `#B49A68` 与铜绿包浆，不用亮金 `#F0CD74`。
   - **金蟾/锦鲤/佛像的色相折中**：不用镜面纯金，改为 **白瓷泥胎暖白 `#E8DFCB` 作底 + 旧金 `#B49A68` 细描线 + 凹处铜锈/泥色**。既守住「低饱和 3+1」，又保住金蟾是「金」的、锦鲤红白可辨。
   - **`GLB_MATS` 四个金色材质需重标定**：`toadGold / toadGoldDark / toadGoldLt / buddhaGold` 目前偏亮金，落到 `v3_*` 新材质后按上方数值下调。
   - **normal 贴图内容是「手绘笔触 / 布纹 / 铸痕」，不是照片级皮肤细节**：在 13 px 高的角色上，照片级法线只会变成噪点。
   - ⚠️ **待裁决（Q13）**：v1 负面提示词明令禁发光特效，但现状 `pondCoinDrop()` 落定用 `emissive` 闪一下、`wishTag` 文字用 `MeshBasicMaterial` 自发光——这些是交互可读性的关键。全禁会让「币落定了没」看不出来，全放又会破坏水墨静谧。
5. **色彩与面积比例**（美术总监定量）：宣纸米 **55–65%** ／ 墨青 **20–28%** ／ 低饱和朱砂 **6–10%** ／ 旧金 **≤5%**；单图 ≤4 色。锦鲤的红白若要保留，只允许「宣纸米鱼身 + 1–2 处低饱和朱砂斑（≤1% 面积）」，**不做高饱和红白/大正三色**（与建模专家的花纹方案有分歧，见 Q18）。
6. **描边**：**取消全身等宽黑 `inkOutline()`**——它会把所有新细节压成卡通。改为 inverted-hull / Sobel 后处理，**1–2 px @1080p、40–70% 透明度**，只勾外轮廓与结构转折（衣缘、耳廓、器口、瓦当）；器物与建筑只靠 AO 分界，不描边。
7. **金色与自发光（Q13 已由美术总监 v3 勘误定案，不再需要裁决）**：**禁大面积 `emissive` / 高亮自发光 / `glow` / `box-shadow` 光晕 / 金色高光渐变**；金只作极细勾线、包边与凹处包浆。**但分三级保留功能性微光，不取消交互可读性**：① `wishTag` 文字与图标用 `MeshBasicMaterial`（现状即可，不加外发光）；② 币落定后用**一次弱 emissive 脉冲**或改为「涟漪 + 气泡 + 币面瞬间反光」；③ 佛前暖光是**真实点光源**，仍为画面唯一暖焦点，不算 glow。判据：静态截图里不出现任何「自己在发亮的物体」。
   - **金蟾折中已定案（Q16 同）**：泥胎暖白底 + 旧金细描线（金色面积 ≤5%、明度 ≤ `#C9B07A`）+ 铜锈**只积在凹处**；佛像改白瓷/泥胎但**不刷铜锈**（否则像出土文物）。
8. **UI 必须同源**（新增，美术总监列为 P0）：放大面板、HUD、入场卷轴的视觉语法统一到「宣纸 / 木轴 / 墨线 / 朱印」——纸色底 `#ECE5D5` + 0.6px 墨青细线 + 木色轴头 + 一枚朱印；**禁用** `backdrop-filter` 毛玻璃、emoji、大圆角白卡、发光胶囊名牌、深棕晕影。虚化只用 `filter: blur()` 且半径极小、静态不用渐变光晕。
9. **删掉所有数值与计数**（新增，P0）：功德、修行时长、今日修行、重置按钮、「全席 50 席」、「第 N 敲 / 第 N 念」、好感度条。`gameplay-spec-v1.md` 早已定「氛围观赏型、零数值」，但代码里 `META.gain`、`save.totalMerit`、`focusCount` 一直没清。卷轴只留当下这一句偈，HUD 只留「此刻庙中另 N 位同修 / 佛前 18 席」。
10. **汉字与钱文规则**：匾额、法号、印章、聊天气泡文字一律走 `plaqueTexture()` / `wishTagTexture()` 这类 PIL + 系统楷体后期合成或 DOM，**绝不交给 3D 模型或贴图去画**（汉字在模型上必乱码）。铜钱上的「乾隆通宝」等钱文，建议**只做浅浮雕凹槽 + 抽象笔画**，不写可辨汉字，既避乱码也避造币考据。
7. **水体**：青灰 `jade` 为底，必须有法线扰动 + 菲涅尔 + 池底折射 + 岸边湿痕；水面下的锦鲤与硬币要有色散/模糊层次，而不是「贴在蓝盘上」。
8. **同源原则**：任何出现在放大面板里的物件，**只能用主 renderer 离屏渲染的 3D 图**，删除对应 CSS 拟物 DOM；光源方向与场景一致。

### 4.1 3D 建模专家复核意见（已并入本规格）

- **动画用 morph targets，不上真骨骼**：现有 `addPeer()` 用 `clone(true)` 共享同一份几何，真骨骼在 Three.js 里需要 `SkeletonUtils.clone()` 且每实例独占骨骼，50 同修成本极高。`clasp` / `bow` / `greet` 三个 morph target + 少量 pivot（`bowPivot` / `tailPivot`）即可覆盖，且兼容现有 `handsRigApply(k)` 的 0→1 插值。
- **和尚合十必须连手掌形状一起做 morph**：现状 `grpHands` 是两个 0.13 半径球体，家位在袍内（胸口 z≈0.52 < 袍面 z≈0.62），只能靠代码把整组手向前「捅」出袍面。新模型要把**上臂/前臂/袖口/双掌**做成一条连续曲面链，合十是肘屈→前臂内收→双掌贴合，头微垂 15°，袖摆滞后一拍；不要再做「两颗球位移」。
- **金蟾靠贴图而不是靠面数**：癞瘤、包浆、蹼纹用 1024² 的 normal + AO 烘焙到连续曲面即可，5–8k tris 足够；不要再用 43 个独立 mesh 去堆 15k 面的纯色球体。
- **`court.glb` 建议「只补贴图、不重做」**：它已是 76 mesh / 62k tris 且质量最好，整体重做收益最低、风险最高（会重接全部交互热点与匾额/壁画/石灯叠加层）。仅补瓦/木/石三张 tileable PBR 与倒角，并统一到 v3 色板。
- **材质命名双轨制（防止 PBR 被覆盖）**：`applyGameMaterials()` 130 会按材质名整份替换成纯色材质；`applyCourtMaterials()` 1186 同理。新模型自带 PBR 贴图的材质必须用 `v3_*` 前缀并避开 `GLB_MATS` 的键名（`skin / robe / robeDark / sash / shoe / bead / eye / highlight / pupil / gold...`），两套共存。
- **9 张 sprite 有时序坑**：`boot()` 里 `buildPropSprites()` 若早于 `preloadGLB()` 完成，会静默用程序化几何渲染旧图。替换 GLB 时必须保证「先 await 全部 GLB → 再生成 sprite」，并在 `console` 里断言每帧渲染的是 GLB 而非回退分支。

### 4.1.2 emissive 定案后的三条建模落地（美术总监 v3 最终更正）

既然 Q13 定为「禁 glow、只留功能性微光」，三处旧的自发光反馈必须**改成形体变化**，不能只是把亮度调低：

1. **拜垫**：新增 `pressed` morph target —— 中心凹陷 0.03–0.05、边缘微鼓、布纹随压痕拉伸；跪下/起身用它表达，删掉发光圈。
2. **心愿灯 / 长明灯**：用**细长火滴 mesh + 一次 0.3s 点燃形变**代替 `MeshBasicMaterial` 常亮自发光；火滴本身低饱和暖色，亮度由佛前真实点光源承担，不加 `glow` / `box-shadow`。
3. **金币**：落底用「扬尘 + 涟漪 + 姿态缓动 0.25s」代替 emissive 脉冲（详见 §5.2），顺带修 `game.js:1946` 的旋转瞬间跳变。

**机读判据**：模型自身 `emissive ≤ 0.15`、强度 `≤ 0.35`、`softGlow` 半径 `≤ 包围盒 1.2 倍`、动效结束即灭；静态截图里不出现任何「自己在发亮的物体」。
**铜锈折中**：只用 `jade #788B80` 与 `wood/ink` 暗褐派生，**不新增独立青绿色相**；铜锈像素不得形成 >3% 连续色块；佛像改白瓷/泥胎但**不刷铜锈**（否则像出土文物）。

### 5.1.1 池塘 y 层次错乱（**硬前置，必须先修，否则锦鲤与沉底币做不出来**）

| 层 | 当前 y | 材质 | 问题 |
|---|---|---|---|
| `ground` 200×200 平面 | 0 | **不透明** `MeshStandardMaterial` | 任何 y<0 的物体被完全遮住 |
| 池底圆盘 | 0.012 | 不透明深色 | 在 ground 之上，但半径/不透明度不足以盖住 `stone.png` 平铺缝 |
| 水面圆盘 | 0.035 | 半透明青蓝 | 只比池底高 2.3 cm，没有真实水深 |
| **池底硬币** | **0.045** | 纯金 | **在水面之上 → 视觉上是「漂着」，不是沉底** |
| 荷叶 | 0.05 | 不透明绿 | 与硬币几乎同高 |
| 涟漪 | 0.06 | 透明环 | 最上层 |
| `pondFish` 基位 | **−0.6** | — | **在 ground 之下 → 常驻锦鲤会被地面挡住，只能靠「跃出」短暂可见** |

**修正方案（3D 建模专家 v1.2 最终定案，取代初稿的「挖洞 + 池底下沉到 −0.45」）**：**不挖洞、不下沉到负值、不动 `court.glb`**。只需把 `pondBed`（`CircleGeometry(POND.r + 0.06, 40)`，`game.js` 动态对象）改成**完全不透明**，放到 `y = 0.015`（高于 `ground` 的 `y=0`），即可盖住 `stone.png` 26×26 平铺缝；再把各层按下面顺序抬升，用 0.015→0.12 的分层做出浅水深与水下层次。

| 层 | 最终 y | 说明 |
|---|---|---|
| `ground` | 0 | 不动，保留 200×200 平面 |
| **`pondBed` 不透明池底** | **0.015** | 半径 `POND.r + 0.06`，不透明，`renderOrder` 最低；这是挡住砖缝的关键 |
| 池底硬币 | 0.028–0.034 | 落在池底之上，随机姿态层叠 |
| 锦鲤巡游 | 0.045–0.085 | 水下层，随游动轻微起伏 |
| **水面** | **0.10–0.12** | 必须**低于 `court.glb` 荷池石沿 0.15**，否则水会漫过池沿 |
| 荷叶 | 0.125 | 浮在水面 |
| 涟漪 | 0.13 | 水面之上 |
| 水花 / 气泡 | 0.14 | 最高层 |

- 水面材质：`transparent: true`、`depthWrite: false`，配合 `renderOrder` 明确分层（池底 → 币 → 鱼 → 水面 → 荷叶 → 涟漪 → 水花），避免半透明排序闪烁。
- **硬判据（写进验收）**：任意视口下，不透明池底必须完整覆盖 `POND.r + 0.06` 且高于 `ground y=0`；水面下**不得出现任何方形线框**；币与鱼必须清晰位于水面之下。
- 此项只动 `buildScene()` 荷池段与 `updatePond()`，与批 2「交互热点零重接」不冲突。初稿提到的「给 ground 挖洞」方案**作废**（风险高、会动铺装与 court.glb 池沿，收益相同）。

### 5.2 建议方案（三层）

**数据层**：`server.js` 新增 `pondCoins`（数组 `{id,x,z,rot,variant,at,by?}`），原子写入 `data/pond-coins.json`（节流 2s，进程启动时载入）。
- 新增消息：C→S `coinDrop {x,z}`；S→C `coinSync {total, recent[]}`（放进 `welcome` 一次性下发 + 之后增量 `coinDropped {coin}` 广播给其他在线者，让所有人看见币落下）。
- **不清理、不设上限、不跨天重置**；不存愿望、不存用户身份（只存坐标与色调，避免隐私）。
- 与 `gameplay-spec-v1.md`「不新增服务端持久状态」冲突，**Q2 已由用户确认按本方案修订 v1 该条**。

**渲染层**：`InstancedMesh` 单几何 + 3–4 材质变体；`recent[]` 只下发最近 300–500 枚用于绘制，`total` 用于 HUD/彩蛋文案。超出绘制上限时，最老的币做「沉入淤泥」处理（下沉 + 压暗 + 不再新增实例），视觉上仍在、语义上仍「不清理」，但 draw call 恒定。
- 落币流程改为：飞行币 → 触底 → **直接写入 instance 矩阵并转为常驻**，删除飞行的临时 Mesh；不再有「发光 1.2s 后消失」。
- **必须修一处现存穿帮**：`game.js:1946` 落定瞬间 `f.mesh.rotation.set(...)` 把还在翻滚的币**直接跳成近水平姿态**。改为落底后 0.25s 内缓动到静止姿态（保留一点点随机倾角），并加一小圈**扬尘/淤泥扩散**代替原先的 emissive 提示，让「币沉到底了」靠物理反馈读出来，而不是靠发光。

**真实感层**（对应搜到的实景参考）：池底铺小卵石与薄淤泥、硬币随机姿态层叠、越旧越暗越绿（氧化）、局部被泥半掩、水面因币面反光有细碎亮点；允许「币多到看不清池底」，但要不要复现到那个程度见 Q2。

**放大面板**：删除 `.coin-water` / `.coinToad` 整套 CSS 拟物 DOM，改为**把真实 3D 池塘（水面 + 池底币 + 金蟾 + 锦鲤）离屏渲染成同源图**，或直接用第二个相机做实时小窗；这样面板里看到的就是院里那一池水。

## 6. 专项二：多人打招呼与「仅两人可见」的聊天

### 6.1 参考依据（已联网核实）

- **《光·遇》(Sky)**：没有公共聊天频道、没有玩家 ID；聊天需好友解锁或两人共坐长椅；**聊天内容只有聊天的两人能看到，第三人看到的是「…」省略号**；气泡在头顶；聊天记录不持久、退出即消失；另有纸船/留言作为文字表达。来源：[18183](https://www.18183.com/skygy/202007/2965110.html)、[7724](https://www.7724.com/remensy/news/83476.html)、[山福游戏网](https://www.csflhgc.cn/sfyxwf/10684.html)。
- **《燕云十六声》**：打招呼＝微点头 + 举手轻挥；鞠躬＝身体前倾、头低垂、双手自然下垂；NPC 不是站桩弹窗，靠近才触发；屋檐猫可上手 RUA。来源：[腾讯新闻](https://news.qq.com/rain/a/20240622A086I700)、[新闻](https://news.qq.com/rain/a/20250402A07SH100)、[姿态动作说明](https://m.wishdown.com/article/512911.html)。
- **threejs.cc**：案例库 840 个作品，可借鉴的是「WebGL 水面」「手绘风柔和叙事」「氛围光影」「写实表面细节」，不是它的大场景性能预算。

### 6.2 打招呼（含「要不要短动画」的评估结论）

**建议：要做，只在双方 3m 内播放，完整行礼 1.2–1.85 秒（核心「合十」只有 0.55 秒，不拖沓）。**
理由：① 合十动画本来就在 P0 要重做，行礼只是同一套 morph 的一个状态，边际成本低；② 燕云/光遇的「人与人感」几乎全来自动作而非文字；③ 有了它，「打招呼」才是一个可被看见的仪式，否则只是弹一个 toast。
3D 建模专家给的完整节奏：起手合十 0.55s → 定住 0.35s → 微躬 0.45s → 回正 0.5s ≈ **1.85s**；若嫌长，可砍掉「微躬」压到 **1.2s**。建议做成常量 `GREET_DUR`，由 Q4 一句话切换，不必改模型。
不做的情况：如果 Q4 选择「不做动画」，则退化为双方转身相对 + 一枚淡墨合十印，仍能传达但不建议。

**动作规格**：靠近到约 2m → 双方面向彼此 → 头微垂 15° → 双掌合于胸前（肘屈、前臂内收、袖口滞后一拍，复用 §4 和尚 `clasp` morph）→ 定住 → 回正；一声极轻磬；**不切镜头、不弹窗、不广播给第三人**。第三人只看到两人转身与一点柔光。
**必须顺带修一个现存 bug**：`monkPoseT` 归零时 `handsRigApply(k)` 的 `k` 直接跳回 0，手会「弹」回原位而没有收手过程。行礼动画要补 **0.5s 收手回落**，并把 `k` 改成对 `claspAmount` 做 `damp` 插值，而不是硬置 0。
被招呼方：轻微回礼（点头 + 短合十）或仅头顶浮一枚淡墨「合十」印，二选一见 Q4。

### 6.3 聊天（光遇式，仅两人可见）

**握手**：点对方 → `greet` → 对方收到 `chatInvite`（头顶一枚淡墨邀请印，不是弹窗）→ 对方点头/合十回礼才建立会话 → 双方进入可输入态。目的是避免陌生人强行打扰，也照搬光遇「需要付出/解锁才能说话」的克制感。

**气泡规格**：
- 挂在 `#labels` 同层，按 3D 头顶坐标做屏幕空间投影（复用 `updateLabels()` 2775 的避让逻辑，避免与法号牌重叠）。
- 宣纸米底 `#ECE5D5`、细墨青边、`border-radius` 大圆角、无头像、无阴影堆叠、无昵称栏；字体沿用卷轴楷体；最多 2 行 × 20 字。
- 淡入 0.25s → 停留 4–6s → 淡出 0.4s；同时最多 2 条/人；连续发送做 1.2s 节流。
- **第三人**：只看到 `···` 三粒淡墨点（光遇式省略号），看不到任何文字；不做公共频道、不做历史、不落库、退出即消失。
- 输入：底部单行宣纸输入框，移动端跟随 `visualViewport` 上移、收起时回位；不抢焦点、不遮挡 dock；回车发送、Esc 收起。
- 位置复用 `updateLabels()` 2775 的 `dy -= 26` 屏幕空间避让，气泡在法号牌上方再叠一级 —— 批 2 刚修好「同修叠人、名牌挤成一团」，别把问题带回来。
- 字数上限复用服务端 `cleanWish()` 已有的 24 字清洗与上限（不必另造轮子）；气泡最多 2 行。

**协议扩展**（`server.js` 现在只有 `broadcast(obj, exceptId)`，需加 `sendTo(id, obj)` 按 `ws._pid` 定向）：

| 方向 | 类型 | 载荷 |
|---|---|---|
| C→S | `greet` | `{to}` |
| C→S | `chatInvite` / `chatAccept` / `chatClose` | `{to}` |
| C→S | `chat` | `{to, text}` |
| S→C | `greeted` / `chatInvite` / `chatReady` / `chatMsg` / `chatEnd` | `{from, name?, text?}` |

服务端只做：长度 ≤ 24 字、控制字符清洗、每人 1.2s 限流、会话双方 id 校验；**不落库、不写日志正文、不广播内容**。

> **隐私红线（美术总监特别强调）**：`sendTo()` 必须按 `ws._pid` **定向投递**，绝不能 `broadcast` 全文再让前端按 id 过滤 —— 后者等于把每个人的私聊内容发给全庙所有人，任何打开控制台的人都能看到，是实打实的隐私事故。同理，聊天内容不进 `presence`、不进任何日志、不进作品集截图。

### 6.4 ⚠️ 本项最大风险：公开实时文字聊天的合规

`gameplay-spec-v1.md` 第 18/20 行明确写着「**不需要云数据库**」「不做共享 UGC、不做内容审核」。但一个公网可访问、可自由输入文字、实时送达的聊天，性质上已经是 UGC，通常需要敏感词过滤、频率限制、日志留存与举报/处置通道。这与既定规格直接冲突，且是本轮唯一可能带来外部合规责任的功能。
**必须在 Q3 先选形态再开发**，四个选项的成本与风险见第 9 节。

### 6.5 社交交互「不能做」清单（守住禅意与合规）

- 不做**世界/公共频道**、不做频道列表、不做在线成员列表点名私聊。
- 不做**持久聊天记录**、不做未读红点、不做消息数角标、不做「对方正在输入」。
- 不做**陌生人强推**：无邀请即可弹字、全屏对话、强制镜头切换、强制音效都属于打扰。
- 不做 MMO 式聊天框：无头像、无昵称栏、无时间戳、无气泡尾巴、无表情包商店、无快捷短语面板铺满屏。
- 不做**广播式私聊**（见上方红线）、不做前端过滤伪装隐私保护。
- 不做「好友/亲密度/蜡烛解锁」等成长系统 —— 光遇的门槛值得借的是「克制」，不是它的经济系统。
- 第三人最多看到 `···` + 两点微光，**不显示任何文字、不显示谁在跟谁聊**；若 Q3 选「预设短句」，连省略号都可省。
- 打招呼短动画**总时长封顶 1.6–2.0s**（与建模专家 1.85s 一致），只在双方 3m 内、且同屏人数 ≤8 时播放；50 人满员时降级为「点头 + 墨印」，避免一院子人同时抽搐。

### 10.2 与规格的偏差（如实记录）

- **未上 morph targets**：和尚 / 猫的动画仍用「节点 Group + 代码插值」驱动，而非 v1 建议的 shape keys。理由：同修 `clone(true)` 共享几何，morph influences 的 per-instance 行为需额外验证；节点方案已能表现合十、且零回退风险。后续如需更细腻的布料形变可再换。
- **court.glb 只字未动**：P2 的瓦/木/石三张 tileable PBR 未补，避免动 76 mesh 的 join 结构。
